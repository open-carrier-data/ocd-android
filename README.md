# OCD Check

> **Early development.** Open Carrier Data is in early development. Data, formats, tools and apps change often, and values can be wrong or missing. Don't rely on it for anything important yet. Feedback and reports are welcome.
>
> OCD Check is a work in progress, version 0.4.7. It has no releases, is not on any app store and is not meant for general use yet.

OCD Check is an Android app that reads a phone's SIM, network and carrier settings and compares them with [Open Carrier Data](https://github.com/open-carrier-data/open-carrier-data) (OCD). Its debug and release builds are read-only: they change nothing on the phone and send nothing by themselves; they make a network request only when you tap for it (OCD's public data with "Get newest data", round 32 U1; the mobile-data path check with "Why is mobile data not working?", round 42 item 2). A separate `owner` build, only for the owner's own phones, tests, applies and reverts carrier settings; see [The owner build](#the-owner-build).

This repository holds two apps, never one APK (OCD's rule round 37, item 6): OCD Check, the Gradle app in `app/`, and **OcdCarrierSettings** in [`carriersettings/`](carriersettings/README.md), the dataset provider a ROM builds into its image with Soong (package `com.android.carriersettings`, platform-signed by the ROM builder, no INTERNET). The app is the provider's only writer; their protocol and its contract tests are in [`protocol/`](protocol/README.md). A ROM adds the provider with one manifest project and `PRODUCT_PACKAGES += OcdCarrierSettingsDataset`, pinned to a `carriersettings/v*` tag.

**Status: early; source public, no releases.**
- **The read-only builds** (debug and release) are stage 2 of the plan (view only, normal app) plus stage 2b (the optional read-only Shizuku deep check); since OCD's round 17 the device records; since rounds 18, 19 and 22 the IMS reader for Android's own IMS (stage 2c), the guided call test (stage 2d) and the hint for a `supported` summary next to `off` device records; and since round 23 the incoming call of the guided call test with a local T2 status, and the guided switch step (AP3). They first ran on a phone on 2026-10-13 (Galaxy A50, Android 14, LIDL Connect SIM). They stay read-only. OCD's round 31 (2026-10-28) ended trigger AV2: the build other ROMs ship is the separate `rom` build type (see **Round 31** under "The owner build").
- **The owner build** (OCD's round 25 and the owner's direction of 2026-10-19 evening; #9 to #15) has run on the owner's S20 since 2026-10-19 as a privileged system app (`/system_ext/priv-app/OcdCheckOwner`), with its page under Settings > Network & internet > Open Carrier Data. It pulls OCD's newest validated `main` commit, pinned by its SHA (OCD's rule round 29, "freshness", 2026-10-24), and tests the carrier settings on and off. It keeps what works and reverts with proof. Its tests run automatically and silently in the background, and it opens a prefilled report issue for the owner to submit; with a token the owner enters, it sends its settled results itself (OCD's round 29). Since OCD's round 30 (2026-10-25) it keeps no value itself: it pulls OCD's whole dataset and hands it to the ROM's CarrierSettings, which installs it, and it tests every changed value together and records what it measured (see **Round 30** below). Since OCD's round 31 (2026-10-28) there is no safe mode: the way back is disabling the app in Android's Settings, and the voice-loss hold keeps the ROM's own data while the values at fault are found (see **Round 31** below). On 2026-10-19 and 2026-10-20 its tests on the S20 with a LIDL Connect SIM kept nothing, because the phone already matches OCD, and every IMS trial was reverted with proof. The first APN trial's revert hid three stock Vodafone rows; "Reset to default" restored them, and #11 fixed the cause. Since OCD's round 26 (2026-10-20) it measures calls itself, so nobody dials or listens: the ladder "signed in → calls out → works", a passive watch of real calls, its own muted mailbox call at night as the fallback (installed in dry-run mode, which only logs what it would dial), the provisional keep of changed voice values, and MMS checked only where the network still offers it, by an access point probe. It is never distributed.

The app is not on any store. The JVM tests pass and the debug build assembles. Only the owner's builds use it. That makes it a named consumer of OCD's data, not a public release. Its first public release fires OCD's trigger T1, and so does a public ROM that bundles it.

## What it does

1. **Reads the phone**, through public Android calls only:
   - **Your SIM:** network code (MCC/MNC), SIM name (SPN), Android carrier ID and specific carrier ID with their names, and GID1 if the permission is granted.
   - **Network now:** serving network code, roaming, the data and voice network types, and three 5G hints: standalone (SA) in use, the 5G icon (`TelephonyDisplayInfo`), and whether the phone reports a 5G signal.
   - **Carrier settings on this phone:** six CarrierConfig keys and nothing else: `carrier_volte_available_bool`, `carrier_wfc_ims_available_bool`, `carrier_vt_available_bool`, `vonr_enabled_bool`, `enabledMMS` and `carrier_nr_availabilities_int_array`. It also reads whether carrier-specific settings were applied at all.
   - **Mobile data connections:** the APN name and the APN types of each mobile data connection Android shows to apps.
2. **Looks the SIM up in OCD's data**, which ships inside the app. It shows the matching profiles, general to specific, and the most specific profile's value for every capability. Each value comes with OCD's own plain meaning from its README, "Limits to read before you ship". For VoLTE, Wi-Fi calling, VoNR and video calling, OCD's value is a summary over every phone model's carrier table; where OCD has a device record for this phone model, the app shows it next to that summary: "this phone model's own file says on" (see "Device records" below).
3. **Writes findings in plain language.** A finding compares a phone reading with an OCD value, for example "OCD's answer is supported; this phone's carrier settings have it off". A finding never says a feature works, that OCD is wrong, or that a carrier does not support something. Whether the phone is signed in for VoLTE or Wi-Fi calling is hidden from normal apps. The app says this needs the deep check and does not guess.
4. **Builds a report** you can read, then copy or share through Android's share sheet. The full text is on screen before Copy and Share appear.
5. **Optionally runs a deep check through Shizuku** (see below): whether the phone is signed in for VoLTE or Wi-Fi calling, on Samsung's IMS or on Android's own IMS (LineageOS and other AOSP-based builds), over which network, for which services, and the last sign-out reason; whether the network offers voice over IMS (VoPS); the Wi-Fi calling switch; whether the carrier's Wi-Fi calling server name resolves, in a lookup by the shell and in the phone's own lookup; the kind of Private DNS server the phone uses; whether Wi-Fi calling is held back after a failed attempt; and the phone's APN list. For a SIM of Vodafone Germany's network (26202) it names Vodafone's DNS location filter as the likely cause when the lookup fails. Without Shizuku the app works exactly as above.
6. **Offers a guided call test** with the deep check (see below): you call your SIM's own mailbox yourself, and you call this phone from your second line and answer it yourself. The app records which network each call used (4G, 5G or Wi-Fi) and your answers on audio. When both calls of one feature pass, it keeps a T2 status for VoLTE or Wi-Fi calling. The results stay in the app on this phone.
7. **Offers a guided switch step** (see below): where OCD's value for this phone is on and the phone has VoLTE or Wi-Fi calling off, it shows both values side by side and opens the right Settings screen. You flip your own switch; the app reads the phone again and offers the call test.

## Permissions, and why

| Permission | Kind | Used for |
|---|---|---|
| `READ_PHONE_STATE` | asked at run time, with an explanation first | GID1, the carrier settings, the data and voice network type, and the list of active SIMs. Android's dialog calls this "make and manage phone calls". The app makes no calls, and this permission shows it none; only the optional guided call test reads, through Shizuku, the state and network type of a call you place or answer yourself. |
| `ACCESS_NETWORK_STATE` | normal | The APN name and types of the mobile data connections, and whether the network is metered |
| `INTERNET` | normal | Two uses, each only on your tap and with no identifier: the data pull you start with "Get newest data" (OCD's round 32, U1), requests to GitHub's API and raw hosts for OCD's public repository; and the mobile-data path check you start with "Why is mobile data not working?" (OCD's round 42, item 2), a few kilobytes to fixed test hosts over the cellular link |

That is the whole list:
- **`INTERNET` only on your tap.** The app sends nothing by itself. It fetches OCD's public data when you tap "Get newest data" (see "Getting OCD's newest data" below), and it sends a few kilobytes of mobile data to fixed test hosts when you tap "Why is mobile data not working?". The check runs only while mobile data is the default network (with Wi-Fi on it asks you to turn Wi-Fi off), waits a short while between taps, and never fetches a carrier page. A report leaves the phone only when you copy it or pick a target in the share sheet.
- **No other access:** no location, SMS, call log or contacts permission, no accessibility service and no `QUERY_ALL_PACKAGES`.
- **No third-party services:** no analytics, no Google Play services and no Firebase.

Without `READ_PHONE_STATE` the app still shows the SIM's network code, name and carrier IDs, and OCD's values for them.

Compose pulls in `androidx.emoji2`. Its startup step would look up an emoji font from a system font provider, which on most phones is Google Play services. The manifest removes that step.

The remaining startup entries come from androidx: `ProcessLifecycleInitializer`, and the profile installer with its receiver. That receiver is guarded by `android.permission.DUMP`, so only the system or adb can call it. It is not a permission the app requests.

The deep check adds three manifest entries, none of them a permission the app holds:
- **Shizuku's provider** (`rikka.shizuku.ShizukuProvider`). Shizuku hands its binder to the app through it. It is exported, as Shizuku requires, and guarded by `INTERACT_ACROSS_USERS_FULL`, so only the system and Shizuku's own server can call it.
- **A `<queries>` entry** for `moe.shizuku.privileged.api`, only to show whether the Shizuku app is installed.
- **Shizuku's own permission name.** Shizuku's provider library asks for `moe.shizuku.manager.permission.API_V23`. The Shizuku app defines it, not Android, and it grants nothing by itself; access comes only from Shizuku's own dialog. The Shizuku server finds client apps by this requested permission and sends them its binder, so the app keeps it. An earlier build removed it, and on the A50 the deep check then never saw Shizuku running.

To check a build yourself:

```bash
$ANDROID_HOME/build-tools/34.0.0/aapt2 dump permissions app/build/outputs/apk/debug/app-debug.apk
```

With the Shizuku libraries in, this prints `READ_PHONE_STATE`, `ACCESS_NETWORK_STATE` and Shizuku's `API_V23`, and nothing else. `ManifestTest` checks the same on the merged manifest of every build.

## What it never collects

The app never reads, stores, shows or reports the following. Most of them are also closed to normal apps by Android.
- IMSI, ICCID or their prefixes
- IMEI, TAC, serial number or Android ID
- any phone number. The guided call test's incoming number is compared with the mailbox short codes inside the parser, in the deep check's process, and dropped there; only "a mailbox code or not" leaves it
- location of any kind: GPS, cell IDs, tracking area, PCI/ARFCN, Wi-Fi names, IP addresses
- IMS or SIP identities
- the build fingerprint, build user or build host, or the baseband string
- APN usernames or passwords
- raw dumps or logs
- anything emergency-related, apart from two yes-or-no checks of the guided call test: whether Android calls the mailbox number an emergency number, and whether an emergency call started during the watch

An emergency data connection is skipped, and the app never dials. The guided call test shows only a short mailbox code from the app's own list, never an emergency or service number. Next to every voice switch it points to, the guided switch step shows OCD's note that emergency calls are not tested.

## What it never does

OCD's rule decisions of 2026-10-18 (round 18) allow passive checks only: with the phone's current settings, when you open the app or tap a check, shown on the phone. So the app never does the following:
- write a setting, a CarrierConfig override or an APN row;
- flip a switch. The guided switch step only opens a Settings screen; you flip your own switch there, and the app never suggests turning a voice feature off;
- force or reset IMS;
- try another setting to see whether it works;
- switch the radio, Wi-Fi or airplane mode;
- place, answer or end a call, open a dial pad, or bring up an MMS connection;
- talk to the carrier's Wi-Fi calling server (ePDG). The deep check only looks up the server's name, and that lookup may send one ping;
- send anything by itself, or run a check in the background. There is no telemetry and no server, and it opens no issue for you. The one check that goes on while the app is not in front is the guided call test's watch: you start it, it reads the call state while you are in the phone app, and it ends when you tap Stop, after 15 minutes, or when the app closes;
- download anything but OCD's public data, and that only when you tap "Get newest data" (or, in a ROM that switched it on, once a day; see "Getting OCD's newest data" below). The only other traffic is the mobile-data path check, on your tap only (round 42, item 2).

Its results never become, withhold or rank an OCD value. A report can only start a review of OCD's sources. A ROM may bundle the app read-only; such a build may add only `READ_PRECISE_PHONE_STATE`.

All of this holds for the debug and release builds, unchanged. Round 23 kept the app read-only in every build; round 25 and the owner's direction of 2026-10-19 make one exception, the `owner` build type, which runs only on the owner's own phones and is described in "The owner build" below. Round 31 ended trigger AV2: the build other ROMs ship is the `rom` build type, which tests only after its person opts in (see **Round 31** under "The owner build").

### Telling carrier failure causes apart (OCD's round 42)

OCD's rule round 42 (2026-10-30) decided what the app adds so it can tell apart *why* a carrier feature fails: a refusal class (read from the modem or IMS code when the build is privileged, from how the data behaves when not) paired with an account-state read (a balance or the carrier's own status SMS) into a plain verdict, for example "Mobile data blocked by the account: balance 0.10 EUR". The shared classifiers and the verdict model are in `core/Causes.kt` and `core/Verdict.kt`; one signal reads "probably", two agreeing signals a plain statement, and the verdict never says a feature is "booked", never names a tariff, changes no value and starts no candidate. It may mark a failed data or IMS test "not counted" only when two signals agree or a definite temporary code says the fault is transient, and never overrides the voice-loss hold, the X5 revert or the emergency refusals.

The live runners read the signals the classifiers sort. **Item 2, the probe ladder** (`core/ProbeNet.kt`, bound to the cellular `Network`): D1 a loopback check, D2 the carrier resolver, a public resolver over UDP 53 and the Private DNS reading, D3 an IPv4 and IPv6 literal and a host name, D4 a plain-HTTP 204 check whose redirect is kept only as "the carrier's portal" or "another host", and D5 the login-free carrier self-care page (owner and `rom` only; it ships with `pass.telekom.de`). The owner and `rom` builds run it automatically only after a measured cellular failure, at most once per SIM per 6 hours, never while roaming or with mobile data off, never under the emergency and call refusals; the read-only builds run D1–D4 only, on the person's tap ("Why is mobile data not working?"), with a short cooldown and no D5, and — holding no `CHANGE_NETWORK_STATE` — only while mobile data is the default network. No run includes a throughput sample. **W1, the ePDG name lookup** (owner and `rom` only; `ProbeNet.epdgLookup`, `core/EpdgW1.kt`, `OwnerProbe.epdgIfDue`): the SIM's standard ePDG name (`epdg.epc.mnc<MNC>.mcc<MCC>.pub.3gppnetwork.org`) looked up once through the connected Wi-Fi network's resolver and once through the cellular network's resolver, each kept only as "resolves", "no address" or "fails", never an address. Only the comparison names a cause: when the mobile network's DNS gives an address and the Wi-Fi's does not, the Wi-Fi-calling verdict reads "Wi-Fi side: this Wi-Fi's DNS gives no address for the carrier's Wi-Fi calling server; the mobile network's DNS does" (the Vodafone ECS case); one resolver alone is never evidence. It runs automatically only after a measured Wi-Fi-calling failure (an IWLAN fail cause, or Wi-Fi calling on over Wi-Fi with IMS not registered), at most once per SIM per 6 hours, asking the cellular resolver only when cellular data itself fails or is the default network; the owner's "check now" compares both. Never roaming, with mobile data off or under the emergency and call refusals. W2 (an `IKE_SA_INIT` to the ePDG) is not built: no IKE packet and no hand-built packet goes to a carrier server. **Item 4, the balance USSD** (`OwnerBalance.kt`, owner and `rom` only, opt-in off by default): one `sendUssdRequest` of the exact free read-only code of the SIM's brand, home network only, a small daily cap. The brand is identified only from the SIM's own provider name (EF_SPN), matched exactly against a small per-brand table (`core/AccountReads.kt`, `BalanceUssd.BRANDS`: Telekom, congstar and fraenk on 26201/26206, Vodafone and LIDL Connect on 26202, each with its SPN and code sources); a network code alone never picks a code, since host networks carry brands with other codes (ALDI TALK's `*100#` beside o2's `*101#`, Kaufland mobil's `*144#` on Telekom). An unknown or ambiguous brand gets nothing sent and the record "balance code not sent: brand not identified" with the codes documented for that network, to dial by hand; no source names an SPN for an o2-network brand, so none is sent there. A menu reply is never answered (it is recorded as "the balance needs a menu step; not read" for the owner to read by hand), and the reply is masked before it is kept. **Item 5, the carrier SMS** (`CarrierSmsReceiver.kt`, owner and `rom` only, opt-in): only a message from a sender on the SIM carrier's own list is classified, in memory, into a fixed class set; only the class, the network and the time are kept, never the text, the sender or a number, and it never sends or replies. Each read feeds the verdict as an account-state read while it is fresh (a balance only on the day it was read, a carrier-SMS class until replaced or 31 days).

Round 42 also fixed what the app **never does**, on top of the list above: no TS.43 entitlement client for Telekom, Vodafone or o2 (no server exists; 1&1's AES stays a single guarded owner-phone experiment, not built); no reuse of the stock `ImsServiceEntitlement` app (it writes provisioning flags); no RCS auto-configuration query (it mints tokens and can send an OTP SMS); no `getSubscriptionPlans`, Mobile Data Plan Sharing or CAMARA; no USSD or IVR menu navigation of any kind; no SMS ever sent or auto-replied to a carrier number; and local CarrierConfig or `getAvailableServices` never count as carrier evidence. The owner and `rom` builds declare `android.permission.USE_ICC_AUTH` next to `READ_PRIVILEGED_PHONE_STATE` for the EAP-AKA `getIccAuthentication` path (Android 16, behind an aconfig flag); nothing uses it yet.

The owner's OCD Lab is a separate tool on a PC, in OCD's private repository (`tools/ocd_lab/`). It applies temporary CarrierConfig test overrides over ADB as root. It is not part of this app, and this app does none of it.

## What a normal app cannot see

Android hides these from normal apps:
- whether the phone is signed in for VoLTE, Wi-Fi calling or SMS over IMS (IMS registration), and its errors;
- the phone's APN list;
- whether the Wi-Fi network's DNS resolves the carrier's Wi-Fi calling server (ePDG). A normal app would need the internet permission for that;
- the network a call actually uses;
- GID2, and OCD profiles that match on ICCID or IMSI. The app lists these as "profiles this app cannot check".

The deep check below reads the IMS registration (on Samsung's IMS and on Android's own), the last sign-out reason on Android's IMS, the APN list and the ePDG name; the guided call test reads the network a call uses. Samsung's IMS errors, GID2 and the ICCID or IMSI matches stay out of reach.

## The deep check (Shizuku)

**Why it exists.** The question people ask most, "is my phone signed in for VoLTE or Wi-Fi calling?", is closed to normal apps. On stock Samsung phones only the shell user (adb) or root can read it. [Shizuku](https://shizuku.rikka.app/) lets an app run code as the shell user after the owner starts it through wireless debugging. The deep check uses that to repeat, on the phone, the read-only adb check the owner ran by hand on a Galaxy A50 (`tools/phone_check.py` in OCD's private repository). That check found the A50's Wi-Fi calling failure: the home network's DNS did not resolve the carrier's ePDG name.

**It is optional.** Without Shizuku, or without your OK in Shizuku's dialog, nothing in it runs, and the report says `"access_tier": "normal"`. The app asks Shizuku for access only when you tap "Allow in Shizuku", and runs the check only when you tap "Run deep check". With results, the report says `"access_tier": "shizuku"`.

**It is read-only.** The whole allowlist is eight commands, a closed Kotlin type (`core/DeepCheck.kt`, `ShellCommand`). Each builds its arguments from constants and two validated values: the SIM slot (0 to 3) and the home network code (5 or 6 ASCII digits). Nothing else can reach a process. For a 26202 SIM in the second slot (index 1), the commands are:

| Command | What it reads | What the app keeps |
|---|---|---|
| `dumpsys secims` | Samsung's IMS state | for this slot: signed in or not, Samsung's state word, the network of the registration (`RAT = 13` LTE, `18` Wi-Fi, `20` 5G), the services (calls, SMS and other known names), Samsung's carrier table name (MNO, for example `Vodafone_DE`) |
| `settings get system wifi_call_enable2` | Samsung's Wi-Fi calling switch for the slot (run only when Samsung's IMS was found) | on, off or not set |
| `ping -c1 -W2 epdg.epc.mnc002.mcc262.pub.3gppnetwork.org` | whether the carrier's standard ePDG name resolves | resolves, does not resolve or not known. Only the first output line is read |
| `content query --uri content://telephony/carriers --projection apn:type:protocol:roaming_protocol:carrier_enabled:mvno_type:edited --where numeric='26202'` | the APN rows for the home network | the listed columns, up to 40 rows; rows identical in every listed column are shown once (Samsung keeps a copy of each row per SIM slot) |
| `dumpsys activity service com.android.phone` | Android telephony's own IMS state (run only when Samsung's IMS is not found) | for this slot's phone: signed in or not, Android's state word (`mImsMmTelRegistrationState`), the transport of the registration log's last sign-in, the services (calls, video calls, SMS), the code and name of the last sign-out reason (`ImsReasonInfo`, never its message), and the phone's own Wi-Fi calling and VoLTE switches (`isWfcEnabledByUser`, `isEnhanced4gLteModeSettingEnabledByUser`; the VoLTE switch only for the guided switch step, not in the report) |
| `dumpsys telephony.registry` | the registry's last known state of this slot's phone | voice over IMS offered on LTE and on 5G (VoPS), and the transports on which the IMS data connection is connected, with LTE or 5G told apart. The guided call test reads the call state, the foreground call state, `mCallNetworkType`, whether `mOutgoingCallEmergencyNumber` changed, and whether `mCallIncomingNumber` is one of the mailbox short codes (compared in the parser, the number never kept) |
| `logcat -d -v epoch -b main -b radio -s EpdgSelector:V IwlanDataService[1]:V EpdgTunnelManager[1]:V` | the lines of Android's IWLAN service in the log, every other tag silenced; `-d` only dumps (run only on Android's IMS) | the phone's own ePDG lookup (whether it asked for the standard name, whether it got an address, how long ago), whether the Wi-Fi calling tunnel is up, the error type of the last refusal, and whether a network back-off timer or Android's retry wait holds Wi-Fi calling back, and for how long |
| `dumpsys connectivity` | the connected Wi-Fi's DNS servers | only their class: in the local network (usually the router), outside it, mixed, none, or not on Wi-Fi |

How the output is handled:
- **Parsed where it is read.** Shizuku starts the app's `DeepCheckService` as the shell user (or root) in a process of its own. That process runs the commands and parses their output line by line. Each line is dropped once it has been looked at.
- **Only typed fields reach the app.** The result is enums, booleans, numbers and short strings checked for shape. IMSI, ICCID, IMEI, phone numbers, SIP URIs and IP addresses have no field to land in; an MNO or APN name with a run of 9 or more digits is dropped. The registry and the phone dump hold phone numbers, cell identities and the emergency number list, and the log holds server addresses; the parsers read none of them into a field. The app decodes the result strictly, so an unknown key or a wrong shape fails.
- **The APN query never asks for credentials.** It reads no user name, password, server, proxy, port or MMSC column, and not the MVNO match value (an SPN, GID or IMSI pattern). Emergency and deleted rows are left out.
- **The ePDG lookup touches the network.** It sends one DNS query through the phone's default network. If the name resolves, the command may send one ping to the carrier's server. The app itself never looks the name up; the shell user does. The app records whether the default network was Wi-Fi and whether Private DNS was on, with `ACCESS_NETWORK_STATE`. From the same network's `LinkProperties` (`getPrivateDnsServerName`, public since Android 9) it also reads the Private DNS server and classes it at once: Google (`dns.google`), Quad9 with ECS (`dns11.quad9.net`), Quad9's default service, Cloudflare, another server, automatic, or not in use. The hostname itself is never kept, because a provider's hostname can carry a personal configuration ID. No shell command is needed for this; the allowlist is unchanged. The lookup is IPv4 only, as in `phone_check.py`, and a carrier may use another server name, so a failure is a strong hint, not proof.

The app never sends a write command. Shizuku's grant could write (`settings put`, `cmd phone`, `content insert`), so tests guard the code (`AllowlistTest`):
- every command in the allowlist, for every slot, is checked against a list of write verbs and shell characters; `dumpsys` may name only the four services above, and `logcat` must be exactly the dump above, never with an option that clears, resizes, rotates or writes a file;
- only `DeepCheckService.kt` may start a process, and only from a `ShellCommand`;
- the app may call only Shizuku's status, permission and user-service methods, never its binder wrapper, remote process or `exit`.

**Android's own IMS (round 18).** On a phone without Samsung's IMS, such as the S20 on LineageOS with PHH IMS, the deep check reads Android telephony's state. The parsers are ports of OCD Lab's (`tools/ocd_lab/lab_parsers.py` in OCD's private repository: `parse_aosp_ims`, `ims_with_pdn`, `parse_registry_phone`, `parse_iwlan_log` with `iwlan_summary`, and `wifi_dns_servers`), and the lab's fixtures from the S20 are their test inputs. The transport comes from where the IMS data connection is, not only from the IMS registration log. On 2026-10-19 the lab found the S20's log still saying Wi-Fi while the IMS data connection had moved to LTE half an hour earlier. When the data connection is connected on exactly one transport, that transport counts, and the log's is kept beside it (`registration_log_transport`) when the two differ.

**Findings.** The deep check adds findings in the same plain style: VoLTE, VoNR or Wi-Fi calling signed in, with a note when the registration log names another network; not signed in for calls over 4G, with possible causes where OCD's tables turn VoLTE on, or with the cell's own statement when it does not offer voice over IMS (VoPS); Wi-Fi calling switched on but not signed in. When the ePDG name does not resolve, in the shell's lookup or in the phone's own, the finding names the A50 fix: Private DNS such as `dns.google`, or fixing the router's DNS (for a 26202 SIM it leaves the advice to the Vodafone note below); with a resolver in the local network it says the router passes the lookup on. When a back-off holds Wi-Fi calling, a finding says by what and for about how long. "Signed in" means the phone registered with the carrier's IMS; it never says a call connects.

**Vodafone Germany's DNS location filter.** Vodafone's name servers answer the ePDG name of 26202 SIMs, `epdg.epc.mnc002.mcc262.pub.3gppnetwork.org` (an alias of `epdg.epc.drz1.vodafone-ip.de`), only for lookups they place in Germany: by the EDNS Client Subnet (ECS) a resolver passes on, or by the resolver's own address. Quad9's default service and Cloudflare send no ECS and got an empty answer when it was measured on 2026-10-19 (the owner's OCD Lab research note `research/ocd-lab-20261018`, "Why some resolvers get no answer for Vodafone's ePDG", in the owner's workspace, not in a repository); Wi-Fi calling then fails without any refusal by the carrier. For a SIM whose home network is 26202 (Vodafone and its MVNOs, such as LIDL Connect), the deep check adds the finding `vodafone_de_epdg_dns_filter` (`core/VodafoneDnsHint.kt`) when the phone is not signed in over Wi-Fi and either:
- a lookup on the phone got no address: the phone's own lookup (Android's IMS) or the shell's lookup over Wi-Fi; or
- the phone's Private DNS is Quad9's default service or Cloudflare, or the Wi-Fi hands out a resolver outside the local network and Private DNS does not override it, and no lookup on the phone got the address.

The finding names the cause and the fixes: the internet provider's own DNS servers on the router (AVM's advice for Wi-Fi calling on a FRITZ!Box), or, on this phone only, Private DNS `dns11.quad9.net` (Quad9 with ECS) or `dns.google`. It says that both of those pass ECS, so the first three parts of the IP address go to the name servers of every name the phone looks up, and that abroad an ECS resolver passes a foreign address, which the filter turns away too. It calls this a likely cause, not a proof. The app does not look the name up itself, since it has no internet permission; it relies on the lookups made on the phone. The DNS finding before it then leaves the advice to it. This is the app's one carrier-specific note. It is about the DNS path, not about a carrier's services, and it never becomes, changes or ranks an OCD value.

**Limits.**
- **The log rotates.** The main log buffer on the S20 holds about 256 KiB, a few minutes on a busy phone. The phone's own ePDG lookup shows only when it is still in the buffer; otherwise the app says "not in the log". PHH IMS's own Wi-Fi calling pause is logged under another tag and is not read.
- **Samsung's IMS errors and back-off stay out of reach.** Samsung's ePDG client does not use AOSP's IWLAN service.
- **Samsung's own ePDG lookup is not read.** Samsung's ePDG client (`com.sec.epdg`) logs to the `EPDG` tag; on the A50 on 2026-10-09 it logged `DNS_QUERY_FAIL` for the empty answer. The deep check does not read that tag, and no failing line has been captured to build a parser on: on 2026-10-19 the A50 had Wi-Fi calling off and Private DNS on `dns.google`, so its ePDG client made no lookup, and `dumpsys secims` holds no lookup result. On Samsung's IMS the Vodafone hint rests on the shell's lookup, which goes through the same Private DNS, and on the resolver classes.
- **One ePDG name.** The shell's lookup is IPv4 only and asks for the standard name; a carrier may use another.
- **Shizuku 11 or newer.** On a phone without root, Shizuku must be started again after every reboot.

## The guided call test (rounds 19 and 23)

OCD's round 19 lists "a guided call test in the app: read-only, allowlisted, observing the call type" as its third step, and defines T2: an outgoing and an incoming call over the feature, each with its measured call type, and the person's confirmation of the audio. Round 23 (LB3, LB4) applies T2 to keeping a value in OCD Lab and sets the wording. The app has both calls. It needs the deep check, because the network a call uses is hidden from normal apps; `READ_PRECISE_PHONE_STATE`, which would show it, is for system apps only.

**What you do.** A T2 test is for one feature, VoLTE (call network type 13, LTE) or Wi-Fi calling (18, IWLAN). Pick it, then make the two calls in either order:
1. **Outgoing call.** The app shows your SIM's own mailbox number, for example 5500 for LIDL Connect. Tap "Start: outgoing call", open your phone app and dial that number yourself. Listen until the mailbox answers, hang up, come back and tap Stop. Say whether you heard the mailbox: yes, no, or not sure.
2. **Incoming call.** Tap "Start: incoming call", then call this phone from your second line (another phone or SIM of yours). Answer it here yourself, check that both of you hear each other, hang up, come back and tap Stop. Say whether both of you heard each other, and whether the call came from your second line.

Airplane mode is not needed (OCD's round 26, rule change 8): the bearer proof below shows Wi-Fi calling instead. A call the phone places over Wi-Fi shows type 18 and counts for Wi-Fi calling, not for VoLTE.

**Which number.** Only the mailbox numbers in `app/src/main/assets/call-targets.json`, a byte-identical copy of OCD Lab's `tools/ocd_lab/call_targets.json`. The SIM's name rule comes first, then its network code (lab `mailbox_for`). Before a number is shown, it must be a plain 3 to 6 digit short code. It must not be on a fixed list of emergency and public-service numbers (112, 110, 911, 116xxx and others) or start with 11, 19 or 0. Android must also not call it an emergency number (`TelephonyManager.isEmergencyNumber`, exact match, which needs no permission). If any check fails, or Android cannot answer, the app shows no number and offers no test. It never falls back to another number. The incoming call needs no number from the app: you call from your own second line. The app never dials, answers or ends a call, and it opens no dial pad.

**What it watches.** Start begins a watch in the deep check's process, separate from the app's. Once a second it runs `dumpsys telephony.registry` and keeps, for this slot, only the call state (idle, ringing, off-hook), the foreground call state (dialing, alerting, active and so on) and `mCallNetworkType`: 13 is LTE (VoLTE), 18 IWLAN (Wi-Fi calling), 20 NR (VoNR), and a 2G or 3G type is a call outside IMS. These are TelephonyManager's network types, as in OCD Lab's `call_type_reading`. Since round 26 (`core/CallMedia.kt`) it also reads, in the same phone block, the bearer proof's other two readings: the transport of the ims data connection (WWAN or WLAN, found by its APN types, since with OCD's `data-2026.10` the S20's ims row is named "Vodafone.de") and the RAT of the WWAN packet-switched registration; and `mCallQuality` (RTP packets sent and received, the call's duration, RTP inactivity, and on AOSP ImsStack also the comfort-noise (SID) packets received, sequence-gap losses, duplicates, the codec and the RTCP round trip; PHH IMS fills it once a second, AOSP ImsMedia every 5 s and when inactivity starts or stops; the silence flags are never read, since no stack sets them) and the disconnect cause (the ImsReasonInfo code and name, never its message). The watch also notes whether `mOutgoingCallEmergencyNumber` changed. For the incoming call it compares `mCallIncomingNumber`, digits only, with every mailbox short code in the bundled table (lab `incoming_number_is` and `allowed_mailboxes`); the app hands the codes to the watch, which accepts only 3 to 6 digit codes. The comparison happens inside the parser, and only "a mailbox code or not" leaves it: the number is never kept, shown or stored. The watch runs in Shizuku's process so that it goes on while the app is in the background, and it stops at Stop, after 15 minutes, or when the app closes. It keeps counts and states only, never a sample list, a number or a time.

**What it records.** The direction: an outgoing call shows dialing or alerting, or goes off-hook from idle without ringing; an incoming call rings first. It also records whether the phone rang, whether the incoming number was a mailbox short code, whether the call went active, the call network types read while it was off-hook (the one read while active is shown), how many calls the watch saw, and your answers. A watch in which no call went off-hook keeps nothing. If an emergency call shows during the watch, the app keeps nothing from it and says so.

**T2.** After each kept call the app assesses the test with OCD Lab's `t2_assess` rules (private `tools/ocd_lab/lab_ocd.py`), ported in `core/T2.kt`:
- The outgoing call counts when it went active, the bearer proof passed for the feature's bearer, every call network type read during it is the feature's (13 for VoLTE, 18 for Wi-Fi calling), and you said yes on audio.
- **The bearer proof** (round 26, automatic check 2, shared with the owner build and OCD Lab): the call type must agree with the ims data connection's transport, and for LTE with the WWAN data RAT (LTE or LTE_CA), both at ACTIVE (the first active reading with a call type) and at hang-up (the last active reading). On PHH IMS 13 is the default call type, so the call type alone never counts. A call whose readings disagree, or that ran on another bearer (19, LTE_CA, is not 13; a 2G or 3G type is not IMS), is "not counted, retry", never a failure.
- The incoming call counts on the same terms, and only when the phone rang, the incoming number was not a mailbox short code, and you confirmed it came from your second line. A mailbox call proves downlink audio only and never counts as the incoming call.
- A call that did not go active, or a "no" on audio, fails the test.
- The app adds two narrower rules: the outgoing call must be measured as outgoing, and a watch that saw more than one call counts for nothing. Round 26 dropped the airplane-mode rule for Wi-Fi calling. In this read-only app the person's yes stays; round 26 says it can only make a pointer there, never a status.

When both calls count and nothing failed, the app keeps a T2 status for the feature; a failed test is shown and its calls stay in the list, and a new test can start. Only passes are kept as a T2 status.

**Wording (round 23 LB4, round 18).** For VoLTE and Wi-Fi calling the app says "registered over 4G (LTE) with these settings" when the deep check reads the registration, and "works on this phone: T2 passed (an outgoing and an incoming call over 4G (LTE), call network type 13, audio confirmed, ...)" only with a T2 pass for the same phone, software and SIM. It never says "works" from registration alone, and no finding says it at all.

**Where results go.** Kept calls, T2 passes and switch steps go into the app's private storage on this phone (`call-tests.json`, schema `ocd-check-call-tests.v2`, at most 50 of each; a version 1 file still reads; the app has no backup and sends none of it). A call holds the date, the phone model, code name, software family, Android version and IMS stack, the SIM's network code and name, the OCD profile that answered, the mailbox brand and short code, the feature and test number, the measurement, your answers and where the settings came from (`as_found`, or `user_toggle` after the guided switch step). None of it is in the report. Round 19 keeps such results apart as a tested status that never becomes an OCD value, and nothing here uploads. "Delete these results" removes the file. A call reads, for example, "An incoming call, call network type 13 (LTE): VoLTE (call over 4G), went active; both of you heard each other; you said it came from your second line." T2 on one phone is not round 19's "seen working", which also needs repeats and other people's reports.

## The guided switch step (round 23 AP3)

Round 23 allows one optional step after the IMS reader, the call test and the round-22 hint: show OCD's value next to the phone's, open the right Settings screen, let the person flip their own switch, read the phone again and offer the call test. The app records `user_toggle`.

**When it is offered.** For VoLTE and Wi-Fi calling only, where OCD's value for this phone is on and the phone has the feature off. Never the other way round: the app never suggests turning a voice feature off.
- **OCD's value** is picked as OCD Lab's `ocd_value` picks it: this phone model's device record on the most specific profile (one for the phone's own software first), else the carrier summary, where `supported` is on and `unsupported` off. A `conditional` or `unknown` summary without a record gives no single value, and no step.
- **The phone's value** is the carrier setting a normal app reads (`carrier_volte_available_bool`, `carrier_wfc_ims_available_bool`) and, with the deep check, your own switch: on Android's IMS `isEnhanced4gLteModeSettingEnabledByUser` and `isWfcEnabledByUser`, on Samsung's IMS Samsung's Wi-Fi calling switch. On Samsung's own software the Android carrier settings are not compared (round 18; Samsung's IMS uses its own tables), so there the step is offered only for Wi-Fi calling, when Samsung's switch reads off.

**What it shows.** OCD's value with its source: the device record (source, stack, newest entry) and profile, or the carrier summary and profile. Then round 18's stack note: a stock record on a LineageOS build is "this model's stock firmware file", which says what the maker's own IMS is set to, not what this phone's IMS can do, emergency calls included; a carrier summary is no file of this phone model. Then the phone's value, what to look for in Settings, and round 10's note: "Emergency calls are not tested. No OCD value has been tested for emergency calls, and this app never places one. Switching VoLTE or Wi-Fi calling on also changes how the phone places emergency calls."

**Which Settings screen.** Public Android intent actions only, tried in order with the general network settings as the fallback. No `<queries>` entry is needed:

| Phone | Feature | Screen |
|---|---|---|
| AOSP-based (LineageOS and others) | VoLTE, Wi-Fi calling | `Settings.ACTION_NETWORK_OPERATOR_SETTINGS` with `Settings.EXTRA_SUB_ID`: this SIM's mobile network page, which on AOSP 16 holds the VoLTE switch ("VoLTE", "4G calling" or "Advanced calling") and, under Calling, Wi-Fi calling. Checked on the S20 (LineageOS 23.2): it resolves to `Settings$MobileNetworkActivity` |
| Samsung's own software | Wi-Fi calling | `TelecomManager.ACTION_SHOW_CALL_SETTINGS`: the phone app's call settings, where One UI keeps Wi-Fi calling. Not yet checked on a Samsung phone |
| any | fallback | `Settings.ACTION_WIRELESS_SETTINGS`: the general network settings |

AOSP's Settings app also has `android.settings.WIFI_CALLING_SETTINGS`, but it is not a public SDK action, so the app does not use it.

**Afterwards.** Back in the app, it reads the phone again as when it opens, and runs the deep check again if it had run before and Shizuku is ready. It shows the readings before and after and asks whether you turned the feature on: yes, no, or "there was no switch" (with the carrier setting off, Settings may not show one). The step is kept on this phone with OCD's value and its basis, source and stack, the screen opened, the readings before and after, and your answer. A yes records `configOrigin: user_toggle`, as OCD's ledger names it, and the call test then offers a T2 test for that feature whose calls carry `user_toggle` too. The app adds no permission and no write verb for this step: `ManifestTest` and `AllowlistTest` are unchanged in meaning, and `AllowlistTest` also checks that the app has no call, dial, answer or settings-write call anywhere.

## The report

The report is JSON with a fixed set of keys. `app.access_tier` is `normal`, or `shizuku` when the deep check's results are in. Its rules:
- **Content:** the SIM's network code, name and carrier IDs, GID1 only if you switch it on, the phone model and its code name (`Build.DEVICE`, which LineageOS uses to name device trees), the Android major version, the software family (`stock`, `lineageos` or `other`), the check results, and the app and data versions.
- **Findings** go in as codes, not sentences.
- **Device records** for this phone model go in under `ocd.device_records`, per capability, as `state`, `source`, `stack`, `newest_entry` and `this_stack` (whether the record holds for the software the phone runs).
- **Carrier settings** go in only as a per-key comparison with OCD's answer (`matches_ocd`), never as values.
- **Deep check results** go in only as typed fields. `ims_registration` is `needs_deep_check` without them. With them, it holds `source` (`samsung_ims`, `aosp_telephony`, `not_found` or `unreadable`), `registered`, `state`, `transport`, `services`, and on Samsung `mno`. On Android's IMS it adds `ims_pdn`, `registration_log_transport` (only when the log differs), `last_disconnect_code` and `last_disconnect_reason`. More blocks join it:
  - `network_offer`: `lte_vops` and `nr_vops`;
  - `wifi_calling`: `switch`, `epdg_name`, `lookup_network`, `private_dns_active`, `private_dns` (`not_in_use`, `automatic`, `google`, `quad9_ecs`, `quad9`, `cloudflare` or `other`, never the hostname), `wifi_resolver`; on Android's IMS also `phone_lookup` (`resolved`, `no_address`, `other_name` or `not_in_log`), `phone_lookup_age` (`under_1h`, `under_1d` or `older`, never a time), `tunnel`, `last_refusal`, `held_back_by` and `held_back_minutes`;
  - `apn_list`: `readable`, `rows` with `apn`, `types`, `protocol`, `roaming_protocol`, `carrier_enabled`, `mvno_type` and `edited`, and `left_out`.
- **Guided call tests** are not in the report.
- **Dates:** the report has the check date, never a time.

Before Copy or Share is offered, every key and string goes through a fail-closed privacy scan (`core/PrivacyScan.kt`). It ports these patterns from OCD's private tools:
- `BLOCK_PATTERNS` from `sanitize_profiles.py`;
- `EXTRA_VALUE_PATTERNS` and the key scan from `field_observations.py`;
- `BLOCKED_RUNTIME_KEYS` from `import_android_runtime_snapshot.py`;
- the SIP/tel URI, IPv4 and IPv6 shapes of `phone_check.py`.

The scan also rejects any key that is not on the allowlist. If anything hits, Copy and Share are switched off, and the screen names the field and the rule but never the matched text. For example, a GID1 made only of digits looks like a long number and blocks the report until you switch GID1 off.

## OCD data in the app

`app/src/main/assets/ocd-lookup.json.gzip` (about 390 KB) is built from a checkout of OCD's public repository by `tools/build_bundle.py`. The script reads these files and changes none of them:

| File | What the bundle keeps |
|---|---|
| `generated/android/lookup.json` | per profile: `profile_id`, `display_name`, `match`, `capabilities`, `newest_entry` |
| `generated/android/metadata.json` | the snapshot's `checks_through`, `stale_after` and `data_digest` |
| `README.md`, "Limits to read before you ship" | the plain meanings of the four capability values and five limit bullets: gates, missing switches, no phone verification, tables not tests, MVNO merge; with device records also the bullet that says what they are |
| `generated/devices/carrier-variants.json`, when the snapshot has it | OCD's device records, whole, after checking that they were built from the same `data_digest` as `lookup.json` |
| `generated/devices/android.json`, with device records | for each catalog device the records name, the device names (`Build.DEVICE`) and models (`Build.MODEL`) that no other catalog device lists |

The bundle also records the source commit and its date. The app shows the data date and warns after `stale_after`.

OCD's monthly releases, `data-YYYY.MM`, support `lookup.json`, `metadata.json` and `carrier-variants.json` for apps (OCD's `docs/releases.md`). The first, `data-2026.10`, was published on 2026-10-19 from public `8cb64d63`, the commit the bundle is built from (#5), so the bundled data is that release's. The script reads a checkout, not a release, and the bundle records the commit. The owner build pulls newer data itself, from OCD's validated `main` rather than the monthly release (see [The owner build](#the-owner-build)); the read-only builds keep the bundled data until you tap "Get newest data" (below).

The app shows the Limits text exactly as the data snapshot ships it. Nothing about an operator's services is hard-coded. The one carrier-specific note, Vodafone Germany's DNS location filter (see the deep check), is about the DNS path.

To refresh the asset or check it:

```bash
python3 tools/build_bundle.py --public ../live-public          # writes the asset
python3 tools/build_bundle.py --public ../live-public --check  # compares only
```

The script refuses a public checkout with uncommitted changes in those files. The output is deterministic: sorted keys and no time in the gzip header. The asset is named `.gzip`, not `.gz`, because the Android build unpacks `.gz` assets and drops the suffix.

**Matching** ports `profile_matches`, `specificity` and `resolve` from OCD's `tools/resolve_carrier_profiles.py`:
- profiles come generic to specific, ordered by specificity, then `profile_id`;
- SPN is compared ignoring case;
- GID1 is compared as a prefix, ignoring case;
- the answer is the most specific profile's value, as `docs/consume.md` says.

Two differences from the resolver:
- **Two carrier IDs.** A SIM has a carrier ID and a specific carrier ID, and a profile's `android_carrier_ids` match when either one is listed. Android's CarrierConfig app compares `cid` the same way (`DefaultCarrierConfigService`, case `"cid"`). The Python resolver takes one ID.
- **Unreadable dimensions are kept aside.** A profile that needs a value the app cannot read (ICCID, IMSI, GID2, or GID1 without the permission) does not simply fail to match. It is listed as "cannot check". The matched stack is the same as the resolver's for the same inputs.

**Device records** (OCD's round 17) say what one phone model's own carrier file sets for VoLTE, Wi-Fi calling, video calling and VoNR on one carrier profile. OCD lists every device value it publishes, including those that agree with the carrier value. The app reads them for the most specific profile:
- the phone's keys are `samsung:` and `Build.MODEL` on a Samsung phone, and the one catalog device whose unique device names list `Build.DEVICE` or whose unique models list `Build.MODEL`, compared case-folded; a name two catalog devices share matches nothing;
- a record whose stack matches the phone's software (`stock`, or `lineageos` on a LineageOS build) reads "This phone model's own file sets VoLTE on for this SIM (one source: Samsung's carrier pack, stock firmware, newest entry 2025-02). OCD's carrier summary is conditional. Configuration, not a test.";
- a record of another stack reads "This model's stock firmware file ...", and adds that the phone runs another software whose own file may differ; it never says "this phone";
- without a record, the summary stays labelled as the carrier's, and the screen says "OCD publishes no file of this phone model for this SIM (none read, older than five years, or not bound to one model)"; a missing record is never "off" and never agreement;
- records built from another data digest than the bundle's are not used.

The app writes nothing from a record into the phone. The findings codes are `device_record_<state>:<capability>` and `device_record_other_stack_<state>:<capability>`.

OCD's round 22 lets a VoLTE, Wi-Fi calling or video calling summary read `supported` where its single-family off and at least one on are device records. So a `supported` summary can sit next to `off` records. Where it does on the most specific profile, the app says so with the correctness ruling's sentence and the count, for example "11 phone models' own files turn Video calling off for this SIM (one maker's or maintainer's files; OCD does not count that as proof)." (`core/LabelHints.kt`):
- under the summary, in the device-records lines, whether this model has a record or not;
- in the `phone_off_ocd_supported:<capability>` finding; the code stays the same;
- in this model's own `device_record_*` finding. When this model's own file is one of the `off` records, it adds that the model's file comes before OCD's summary.

Only the three switches step 2 can label count, and only records built from the bundle's own data. `LabelHintTest` checks it on O2 DE (`26203`) video calling, as round 22 orders, with the records the public `carrier-variants.json` holds and the label set to `supported` as step 2 makes it. Since 2026-10-19 the bundled asset is from public `8cb64d63` (#280), the first publish with step-2 labels and the commit of release `data-2026.10`: O2 DE (`26203`) video calling now reads `supported` in the bundle, so the hint shows on a phone with an O2 SIM.

The bundled data is OCD's. The OCD contributors waive their own rights in it under CC0 1.0; see OCD's `DATA-LICENSE.md`.

### Getting OCD's newest data (round 32, U1)

OCD's rule round 32 (U1) lets the read-only builds pull OCD's newest validated `main` commit through the owner build's path, so they stop showing stale data. They stay read-only: they write no setting, try no other value and send no report.
- **Only on your tap.** "Get newest data" starts a pull. On metered mobile data it downloads at most once a day; on Wi-Fi any time. A ROM that bundles a read-only build may switch on a daily check instead (the overlayable `ocd_daily_data_check`, off by default; `phone/DailyDataCheck.kt`), from the app's first start after each boot.
- **F1 to F3 and the git blob check** (`core/PublicPull.kt`). `main` is resolved once to a commit through GitHub's public API without a token, and every file is read at that commit. Only a commit whose `validate` check run (GitHub Actions) passed is taken; `main`'s newest four commits are walked back for one, and a pull never moves back. Each file's git blob SHA-1 must equal the commit's tree, read from the contents API. A file in a `schema_version` this build does not read refuses the whole pull. `metadata.json`, `carrier-variants.json` and `lookup.json` must agree on the data digest. The validate verdict is the owner build's (`OperatorsPullTest` runs both on the same answers).
- **Only GitHub's hosts, no identifier.** Every request and every redirect is checked before it is sent: https, `api.github.com` under `/repos/open-carrier-data/open-carrier-data/`, or `raw.githubusercontent.com` under `/open-carrier-data/open-carrier-data/` (`PublicData.allowed`). The URLs name the repository, a commit and a path; the only headers are a fixed `User-Agent: ocd-check` and GitHub's API version. `phone/PublicDataPhone.kt` is the only file in these builds that opens a connection (`AllowlistTest`).
- **What it reads.** `generated/android/metadata.json` and `lookup.json`, `generated/devices/carrier-variants.json`, and the operator statements with the carrier-identity table (`generated/operators/`). The README limits text and the device alias map stay the bundled ones. A pull uses at most 9 of GitHub's 60 unauthenticated API calls an hour.
- **It falls back closed.** A failed or refused pull keeps the previous good pull, or the bundled snapshot, whole; the screen says why.

### What the operator states (round 32, part A)

OCD publishes what operators, brands and MVNOs state on their own pages (`generated/operators/statements.json`, CC0) with a carrier-identity table that says which operators and brands run on which networks. The app shows the statements for the SIM's operator or brand, in part A's words, and never uses them as a setting:
- an offer reads "The operator states it offers VoLTE (calls over 4G) (read on 2026-10-28); whether your tariff includes it is not checked";
- an end reads "The operator states MMS ended on 2026-06-29";
- it never says "works", and "Wi-Fi calling abroad" is the operator's word, apart from OCD's `wifi_calling_roaming`;
- a host-only brand (LIDL Connect, ALDI TALK and others: no source states a selector for them, so no phone tells their SIMs from the host's) appears only under "brands on this network", never as a statement about the SIM;
- a network-wide statement (an operator's MMS end) reaches every SIM on that network.

The SIM's identity entry is the one whose selector maps to the SIM's most specific OCD profile, else the operator of the network's plain selector (`core/OperatorStatements.kt`, `OperatorStatementsTest`). The read-only builds show the statements after a pull; the owner build reads them at its pinned commit and shows them under Details, "What the operator states".

## The owner build

The `owner` build type is the owner's part 2, built as he directed on 2026-10-19 evening ("develop it exactly like this"; OCD's private `research/rule-decisions-20261006/README.md`, "Owner direction, 2026-10-19 evening" and round 25). It is for the owner's S20 (LineageOS 23.2 userdebug, PHH IMS) only. It is never a release asset, a CI artifact (the build refuses to package it when `CI` is set), a store build or part of a ROM anyone else runs.

**Its form: a system app with a Settings entry** (the owner, 2026-10-19: "more of a system app and less of a user app — a system service that does all of this in the background, and a UI you can access through the settings, like an 'Open Carrier Data' entry in the settings"). The owner build has no launcher icon. It is installed as a privileged system app, and its screen is **Settings > Network & internet > Open Carrier Data**, between SIMs and Airplane mode, with a live summary that is the screen's headline ("All signed in on your phone's own settings", "Open Carrier Data switched on VoLTE", "A test failed — your own settings are back"). See **The owner screen** below. Everything also runs without the screen, and as quietly as the owner asked on 2026-10-20 ("as automatic as possible but still as silent as possible"): the boot and SIM-change reconcile, the hourly quiet job with its light check and the night's tests, and the update pulls are WorkManager jobs started by `OwnerBootReceiver` (boot, the app's own update, carrier-config changes) and the app's start. See **Quiet background** below.

How the entry works: Settings lists activities with the action `com.android.settings.action.IA_SETTINGS` from **system apps only** (SettingsLib `TileUtils.loadActivityTiles` skips any `ResolveInfo` that is not `system`) and files them by the meta-data `com.android.settings.category`; `com.android.settings.category.ia.wireless` is `CategoryKey.CATEGORY_NETWORK`, the Network & internet screen (`NetworkDashboardFragment`). `OwnerActivity` carries that filter with the title, the icon (tintable), the order (-10) and `com.android.settings.summary_uri`, which Settings calls (`getDynamicSummary`) on `OwnerSettingsProvider`; the provider answers only the system uid, root, the shell and the app itself. The activity is exported but guarded by `MODIFY_PHONE_STATE`, which Settings (the system uid), Settings search (SettingsIntelligence) and adb hold and a normal app cannot get. Installed as a user app the entry does not appear, and the screen opens only with `adb shell am start -n io.github.open_carrier_data.check.owner/io.github.open_carrier_data.check.owner.OwnerActivity`.

**What it does.**
1. **Loads the data and pulls updates** from OCD's validated `main`, not from the monthly release (OCD's rule round 29, "freshness", decided 2026-10-24; the owner: "we want to ship allways the newest data and in the fastest way"). Releases stay the channel for consumers that do not verify on a phone. A pull (`core/MainData.kt`):
   - **F1, one commit pin.** It resolves `main` once to a commit SHA through GitHub's public REST API, without a token (`GET /repos/open-carrier-data/open-carrier-data/commits?sha=main`), and reads every file at that SHA (`https://raw.githubusercontent.com/open-carrier-data/open-carrier-data/<sha>/generated/...`), never at the branch name, so a pull during a publish cannot mix two commits. The files are `generated/android/metadata.json`, `generated/android/lookup.json`, `generated/devices/carrier-variants.json` and `generated/android/apns-conf.xml`. The SHA is recorded in the state (`pin`, with the commit's date, the passing check run, each file's SHA-256 and the previous pin), in the log, in the device log (tag `OcdCheckData`) and in every pointer report.
   - **F2, validated only.** It takes only a commit whose `validate` check run (the job of OCD's `.github/workflows/validate.yml`, from GitHub Actions, on exactly that commit) concluded `success`, read from the public check-runs API. A failed run outweighs a passed one, a run still going is not a pass, and skipped runs (OCD's daily schedule skips the job) decide nothing. When the newest commit has none, it walks back along first parents, at most four commits; reaching the current pin first means nothing newer passed, so a pin never moves back. Otherwise it keeps the current data. Up to date costs one API call, a new pin two, and the walk at most five, against GitHub's 60 unauthenticated calls an hour.
   - **Integrity.** The data digest cannot be recomputed on the phone, so it must be the same in `metadata.json`, `carrier-variants.json` (`based_on_data_digest`) and the `apns-conf.xml` header. Each file is parsed whole and strictly: the JSON files completely, `apns-conf.xml` as well-formed XML without a DOCTYPE, with as many `<apn>` elements as the line reader that later reads its rows. With the pin this replaces the release's `SHA256SUMS`.
   - **F3, schema guard.** It refuses a file whose `schema_version` major it does not know (1 for all three JSON files today) and an `apns-conf.xml` or `metadata.json` of another APN version than 8. Nothing of such a pull is used: the last good data set stays whole, and the log says why.
   - `lookup.json` has no APN rows; they come from `apns-conf.xml`. Until the first pin, the bundled snapshot is used for the IMS values. A tagged release pulled by a build before round 29 is no longer read; its folder goes with the first pin.

   Pulls run once a day on Wi-Fi (the quiet job, below; every six hours while nothing is pinned yet), when the owner taps "Check for update", and first thing in "Test now", so a test runs on the newest data; a pull that fails there never holds the test up. Every pull also fetches OCD's `observed/summary.json` (others' reports, see **Others' reports** below).
2. **Tests every entry, on and off.** For each SIM and each IMS switch (VoLTE, Wi-Fi calling, video calling, VoNR, SMS over IMS) it reads the phone's value and its evidence, then sets the other value as a test override, waits up to 120 s for IMS to register with the feature's service on its bearer (or for the service to go), reverts with proof, and waits up to 120 s more for the baseline to show again (IMS registered as before, on the same kind of bearer, with the same services; logged as "restored"). It changes only what cannot outlive the test (the research report "Safe APN tests and quiet background checks", 2026-10-20): a non-persistent CarrierConfig override, and an APN test row no stock row can match. It never switches Wi-Fi and never touches a persistent setting.
   - **VoLTE while IMS runs over Wi-Fi** is measured inside the non-persistent override `carrier_wfc_ims_available_bool=false`: QNS then qualifies cellular for IMS, which registers over LTE while Wi-Fi keeps carrying the internet; reverting brings IMS back to Wi-Fi. One change measures two things (VoLTE over LTE, and Wi-Fi calling gone with it off). The IMS registration callback tells a fresh REGISTER over LTE (the stronger result) from a stack that kept its registration. If IMS stays on Wi-Fi, VoLTE counts as not measured, not as failing. The log says `volte_method: wfc_override`. The Wi-Fi-off measurement of the first builds is gone.
   - **A voice path stays** through every off value: VoLTE off only while Wi-Fi calling carries voice (and the trial reverts at once if that goes); Wi-Fi calling off (and VoLTE's measurement) only with LTE in service, voice over PS offered and VoLTE on; VoNR off only with IMS registered. Otherwise the off waits (`no_voice_path`).
   - **Video calling** is "not available on this build" from static checks, without a trial: PHH IMS has no video (it masks the capability, has no video call provider and offers audio only), the device flag `config_device_vt_available` is off on the S20 tree, and neither carrier offers ViLTE. On another stack a trial still tells, within the normal 120 s.
   - **APN rows.** For OCD's internet rows for the SIM that the phone lacks, it inserts a test row as AOSP Settings adds an APN: an empty numeric, mcc and mnc with the SIM's own carrier ID, `infrastructure_bitmask=1`, `apn_set_id=0`, no `ia`, wildcard, `ims` or `emergency` type, and marked edited (never `edited=0`, whose delete only hides the row and leaves a tombstone a later identical insert would revive). It records the preferred APN and a hash of every visible row first, reads the new row back by its ID, makes it the preferred APN and waits for mobile data to validate; the revert puts the preferred APN back, waits for internet on it, deletes the test row by its own ID and hashes the other rows again. A null insert answer, a row that reads back otherwise, or another row that changed is a stop. It never updates a row, never deletes by marker and never calls "Reset to default".
   - VoNR's on-test stops before any change on the S20: its modem has standalone 5G switched off.
3. **Finds the best working value** (until round 30 it was applied locally as a kept override; round 30 keeps none, and the first start of a round 30 build drops the keeps of earlier builds once, with proof): on when on registers; else off, when off works and, for a voice feature, a call of the owner's own went active with it off; else the phone's own value. An APN row is kept only when mobile data works with it and not without it. An OCD row that matches a phone row on the telephony provider's UNIQUE columns (APN, protocols, proxy and MMS fields, MVNO match and the rest, but not the name or the types) is the phone's own APN already and is not tested (`same_as_phone_row`). On the first APN step on the S20 (2026-10-19) inserts with the stock key merged into three stock Vodafone rows, and the revert then hid them; the carrier-ID test row cannot share a stock row's key, and nothing is deleted but the test row by its ID.
4. **Re-applies at boot and on a SIM change** (builds before round 30, which kept overrides). Overrides live in memory and a reboot drops them, so after a boot (once the 10 minutes in which a change is refused have passed) the start-up pass applies the keeps of the SIM in each slot again. It is a plain background job, and Android batches those: on the S20 (`min_ready_cpu_only_jobs_count=3`, `max_cpu_only_job_batch_delay_ms` 31 minutes) a lone one can wait up to half an hour more, so the pass comes 10 to about 40 minutes after the boot. A keep of a SIM that left its slot is cleared.
5. **Tests again** on a tap ("Test now", or `--ez test_now true` over adb, see **Round 30**), at once: no wait for the screen, charging or an idle moment, only the refusals that name a harm.
6. **Uploads** by opening a prefilled issue on OCD's "OCD Check report" form in the browser ("Open report on GitHub" in Details). The owner reads it and submits it himself. Optionally, with a fine-grained token the owner enters on the phone, it also sends its settled results itself (**Automatic reports** below); without a token it sends nothing. The issue holds exactly one JSON block, a closed **pointer report** (`core/IssueReport.kt`, `core/Pointers.kt`) that follows OCD's public `schemas/ocd-check-report.schema.json` (`ocd-check-test-report`, version 1) field for field. A report points, phones prove (the anti-fake research of 2026-10-20): every result names an entry of the closed list of the OCD data the run used, never a value: `volte:on`, `volte:off`, the same for Wi-Fi calling (`vowifi`), SMS over IMS, video calling and VoNR, or `apn:` and the row key of OCD's APN row (the APN in lower case, the types sorted, the protocol). Each result says whether it is OCD's value for this phone and SIM (`ocd`) and the phone's own (`phone`, observed; the other value is tested), and gives the result class:
   - `works`: an on entry signed in with calls both ways measured by this phone on its bearer (round 26 L3, which replaces T2's person's yes; the report's call test `t2`), an off entry of a voice feature with a call of the owner's own active, or an APN row with mobile data validated;
   - `signed_in`, `service_off`: the value took effect, no call;
   - `not_possible`: the modem, the IMS stack or the network's offer;
   - `failed`: measured and did not work, or the test broke (the reason says which);
   - `not_tested`, with the reason.

   Since OCD's round 29 a result of `volte:on`, `vowifi:on` or `sms_over_ims:on` can carry **`settled`** (`core/Settled.kt`): what this phone measured under rounds 26 to 28 on this ROM build, as a pass at L2 (calls out, one leg) or L3 (works, both legs on the same bearer), SMS both ways, or a clean measured failure (the measured outgoing or incoming failure, or "no audio stream received" twice on passive calls, the same rules that revert a provisional keep). It names the level, the bearer, the method (`mailbox_call`, `real_call`, both legs, or `self_sms`) and the UTC day the level was reached, never a value, and the report then names the ROM build (`device.build`: `Build.ID` and the build's UTC time, for example `CP2A.260605.016 1792814506`, never the fingerprint, the incremental or the builder). A level attaches only to a run that names the data commit and ran on the same build, and only where the run's own result is signed in or works; a failure turns that result into `failed`. From the owner's account the public bot records these as "re-tested by OCD" in `observed/retested.json` for 90 days after each measurement (public #293). SMS both ways settles when the data SMS to the phone's own number went out and came back over IMS by Telephony's own word on each leg (below, **Optional incoming SMS check**); IMS registered with SMS at the send and the receipt alone never settles it.

   Beside the results it holds the data commit and its data digest (OCD's round 29 S13: the pinned `main` commit, or the commit the bundled snapshot was built from; a run recorded before round 29 names its release tag), the phone (model, codename, Android major, ROM family, build type, IMS stack from the installed ImsService: `phh_ims` for PHH IMS, `samsung_ims` for Samsung's, `aosp_imsstack` for Google's AOSP ImsStack `com.android.imsstack` (the S20 on LineageOS 24.0), `other` for another one, `not_known` when none can be read), the SIM (network code, carrier ID, SPN, and the GID1 prefix of the matched profile, never the whole GID1), the matched profile, the app version and the test date. Empty fields are left out. The text passes the privacy scan first. The URL stays under 6,900 characters, and so does the login URL a signed-out browser is sent to. GitHub answers 500 above about 7,000 for either (measured 2026-10-20), so APN results are left out and counted to fit. The app shows and logs the report's SHA-256 hash (log tag `OcdCheckReport`, with the URL), the same hash the public bot posts. The bot checks that the commit is on OCD's `main` and carries that digest (a release by its tag for older reports), checks every pointer against that commit, and records a valid report under `observed/` as "reported, not checked by OCD". A report is a hint: it never moves an OCD value and never makes a phone skip its own test. At most it makes a phone test that entry earlier (**Others' reports** below). The app remembers the hash of each report it opened, so the owner's own reports are never counted as others'. `ReportSchemaTest` checks the reports against copies of the public schema and form in `app/src/testOwner/resources/public/`.
7. **Runs on its own, silently** (see **Quiet background**): a light read-only check while the phone lies unused, and one feature a night when something is due. The owner's "Test now" tests on values by default; its "Test the off values too" adds the off values at once (otherwise the night tries them one at a time). The background can be switched off.
8. **Measures calls itself, nobody dials or listens** (OCD's round 26, `r26-agreement.md`, and the coordinator's refinements of 2026-10-20; see **Calls, round 26** below): the evidence ladder "signed in → calls out → works"; a passive watch of every real call; the owner build's own muted call to the SIM's mailbox at night only as the fallback; a changed voice value kept for now until calls out and incoming are seen; "re-tested by OCD" from this phone's measured calls. MMS is not tested where the network ended it, and elsewhere only an MMS access point probe runs, never an MMS.
9. **Reverts smartly.** Every start looks for leftovers: a trial left by a crash or a kill is reverted with proof, a trial still live after a reboot is a stop event, and a marked APN row the state does not keep is removed. While a test runs, a quiet notification (the lowest importance: no sound, no status-bar icon, folded in the shade) offers "Stop test". Round 30 removed Undo per entry, Undo all, and Undo in the notification and the Settings entry; round 31 removed safe mode: the way back is disabling this app in Android's Settings (Apps, Open Carrier Data, Disable), after which CarrierSettings serves the ROM's own data without it. Routine work posts nothing; a normal notification comes only when a kept value came or went, or when something failed (a stop event, a baseline that did not come back). The Settings entry's summary is the screen's headline.

**The owner screen** (redesigned on 2026-10-20 for the phone's owner and, later, people who are not technical): a Settings page that answers at a glance whether the phone runs on the best carrier settings, whether Open Carrier Data changed anything, and gives a fast way back. It uses the system's dynamic colour and font (the DeviceDefault font Settings uses, Google Sans Flex on the S20's LineageOS build), in light and dark, and plain words; the technical text is only in Details.

"Calls out" never claims anything about incoming calls, and "(audio from packet counts)" is said only in Details. Each rung needs the one before it; they fill in the status colour as far as the evidence goes. Four fixed colours mean one thing each: works (green), a change Open Carrier Data made or a test running (amber), a problem (red), not possible now (grey, a single cross: "Not offered by your network", "Didn't sign in when tested"). Features this phone never supports (VoNR on the S20's modem, video calling on PHH IMS) leave the list for one muted line ("Video calling and VoNR aren't supported on this phone"); the reason is in the report and the log. The ladder fills once when a new result comes in while the screen is open, never on load, and not at all with animations off. Before the first check and without a SIM the sections are hidden.

**Quiet background** (the owner, 2026-10-20: "is it possible to handle this more in the background so the user does not notice it that much?", then "it should still be as automatic as possible but still as silent as possible"; the schedule follows the research report of the same day):
- **The hourly quiet job** (`owner-quiet`, WorkManager, while Android counts the phone idle) does nothing while the screen is on or a call is up. Otherwise it pulls OCD's newest validated `main` commit once a day on Wi-Fi and runs the **light check** every six hours, and every hour of the night: it reads the carrier config, the registry and IMS, changes nothing, settles every entry it can see without a change (the value the phone has, when IMS shows it) and the static ones (VoNR on the S20's modem, video calling on PHH IMS), re-applies a keep a reload dropped (through the reconcile), and logs only what is new. Nothing due: that is all, and the Settings entry says "checked, nothing changed".
- **Entries and triggers.** Each SIM has an entry per feature value ("volte:on", "volte:off", ...) and one per OCD APN row it lacks. An entry is due on a trigger (a new SIM, new data values for the SIM, a new ROM or app build, a kept value that fails, a switch whose value changed under the app, a test that did not decide) and otherwise in rotation, once two weeks old. New data values means a change for that SIM, not a new commit (OCD's round 29 F4): `main` publishes several times a day, so an entry becomes due only when the OCD answer of the SIM's matched profile changed for one of the five switches on this phone (its value, capability or device record) or an APN row of the SIM's scope did, against the previous pin (`DataBasis`). A pin that changes nothing for the SIM triggers nothing and does not restart the on-values-only nights.
- **Others' reports** (the anti-fake design of 2026-10-20, "a report points, phones prove"; OCD's private `research/rule-decisions-20261006/README.md`, "Owner direction, 2026-10-20: report upload and the anti-fake design"). Each pull (the daily one and "Check for update") fetches `observed/summary.json` from the public repository's `main` (`https://raw.githubusercontent.com/open-carrier-data/open-carrier-data/main/observed/summary.json`, public #286). It is kept only when it passes: at most 2 MB (the read stops one byte past the cap), strict UTF-8 JSON, and OCD's public `schemas/observed-summary.schema.json`, of which the owner build carries a copy (`app/src/owner/assets/`) and which it checks with the same keyword subset as OCD's validators (`core/SchemaSubset.kt`). A fetch that fails, offline included, or a summary that does not pass keeps the previous copy (`files/observed/summary.json` and the state); the log says why. Of the summary the app keeps only this phone model's cells, and in them only the entries others reported `works` or `signed_in`, or `contested` (a clean measured failure). The owner's own counted reports are taken out: when the app has opened a report, it reads the records (`observed/reports/issue-N.json`, at most 20 a pull) of the issues in those cells and compares their `report_sha256` with the hashes it opened; a record that cannot be read counts as someone else's, which can only move a test earlier. For each SIM's own cell (this phone, the OCD profile the SIM matches, its network code, the ROM family, the IMS stack and the Android major, the public tool's `cell_of`), such an entry that the phone has not tested on a later day than the newest report becomes due the next night (`reported_by_others`), ahead of the plain rotation and behind the triggers. That is all a report does (`core/ObservedReports.kt`, `QuietPlan.plan`):
  - it only moves an entry the plan already has (the five switches' values and the SIM's OCD access point names of the release); a report naming anything else finds nothing;
  - it never skips, pauses or removes an entry, never lifts a pause, an undo or the on-values-only nights after an update, and is never a trigger, so it never takes a test out of the night;
  - the test it moves is the same test, so a failure is reverted as always and nothing is kept on a report's word; and it never counts toward "works": nothing of it reaches the runner, the ladders, the headline or the pointer ledger.

  Details shows one plain line per such entry, for example "Others reported VoLTE on works on this phone model — tested first tonight", or "— tested on this phone since", "— checked on this phone without a test", "— paused on this phone after two failed tests".
- **One feature a night**, at most one off value and two on values, between 02:00 and 05:00, and only when all of these hold: the screen off for an hour, on the charger with at least 50 %, no call (by Telecom and the registry) and the audio mode normal with nothing playing, on Wi-Fi, under 50 KB of other apps' traffic a minute (sampled for a minute), no alarm within 45 minutes, not roaming, and IMS registered for voice with mobile service at home. A trigger that waited three days for such a night may use any silent window; a kept value that fails is reverted (dropped) in any silent window. After a ROM flash or new data values for a SIM, only on values run for two nights. Two failures of an entry in a row pause it for four weeks.
- **Each step** of the night's chain looks at the window again, arms an exact revert alarm (`RevertAlarmReceiver`, which queues the cleanup if a step died) and disarms it at its end, keeps to 120 s for the trial and 120 s for the baseline to come back, and stops within a second, reverting what it changed, when the screen comes on, a call rings, the audio mode changes or the charger is pulled; JobScheduler stopping the job does the same. The chain then stops and the quiet job tries again later. A night's session ends after 20 minutes. A voice off is kept only with voice measured, which never happens in the background.
- **What the owner sees**: nothing for routine work; the quiet notification only while a test runs ("Testing a carrier setting", "Stop test"); a normal notification only for a change or a failure; the last result under the Settings entry. The power-save allowlist (`app/src/owner/priv-app/sysconfig-ocd-check-owner.xml`, `/system_ext/etc/sysconfig/`) lets the night jobs and the revert alarm run in doze.

**Calls, round 26** (OCD's private `research/rule-decisions-20261006/round26-20261020/r26-agreement.md`, automatic checks 2, 4, 5 and 6, and the coordinator's refinements of 2026-10-20). No person is needed for any entry, night or release: nobody dials, listens or sends an MMS.
- **Levels** (`core/Calls.kt`, `CallLevels`), per phone × SIM × ROM build and IMS stack × feature × bearer:
  - **calls out (L2)**: an outgoing call went ACTIVE, the bearer proof passed, round 28's media rule passed (below), no SIP failure, and it ended normally (the app's own call: the phone hung up itself, `CODE_USER_TERMINATED`). A real call the owner makes anyway, measured passively, counts the same as the app's mailbox call; a real call nobody answered says nothing;
  - **works (L3)**: calls out plus an incoming call on the same bearer that rang, was answered, did not come from a mailbox code, went ACTIVE with the bearer proof, passed the media rule and lasted at least 20 s.

  Packet counts show an audio stream, not sound, so every Details line that names a level says so ("(audio from packet counts)", "packets only", "No sound was checked"); the works detail reads "answered incoming call with an audio stream both ways (packets)".
- **The media rule, round 28** (`core/MediaRule.kt`; OCD's private `research/rule-decisions-20261006/round28/ruling.json`, decided 2026-10-23). It replaces round 26's single 300-per-10-s test, which a working call with a silent far end fails (a silent AMR or AMR-WB sender sends only comfort-noise packets, about 62 per 10 s), for every call kind:
  - the window: each direction over the whole ACTIVE, non-held window, from the first CallQuality report to the last, at least 10 s and 3 reports (on AOSP ImsMedia's 5 s reports about 15 s connected), received packets net of duplicates; a hold, or a call held beside it, ends the window and the call is "not counted";
  - **full rate** (every stack): at least 300 packets per 10 s and no RTP inactivity; on a stack whose sequence-loss counter is verified filled (`aosp_imsstack`) the received direction also needs at most 20 % sequence-gap loss, whatever its count (the stricter reading of the ruling's mailbox section); stacks without a verified loss counter keep the plain 300 floor;
  - **DTX** (only on `aosp_imsstack`, whose SID and sequence-loss counters a Lab run showed filled on 2026-10-23; never PHH or an unknown stack): below 300, at least 40 per 10 s over the window and in every report interval, no inactivity and no empty interval, and for the received direction at least 20 SID packets per 10 s, at most 20 % sequence-gap loss and AMR or AMR-WB (EVS waits for its own measurement). The sent direction counts on rate and continuity alone, labelled "low send rate, DTX assumed, not verified";
  - verdicts: pass, "Audio stream not judged, retry: …" (a low rate the SIDs do not explain, heavy loss, a short window, EVS, a stack without the counters, a hold, a passive call ended with `CODE_SIP_*` or `CODE_MEDIA_*`), or "No audio packets received for … s after the call connected". Only the last is ever a measured failure: at once on the app's own mailbox call, and for a passive real call only after two such calls on the same SIM and bearer on separate days, each with the bearer proof (`CallLevels.noStreamTwice`). A mailbox call that passes only as DTX carries `mailbox_below_full_rate` for Lab review;
  - each call's `media` in the ledger carries the ruling's fields (call kind, IMS stack and build, rule version, bearer verdict, window, report count and largest gap, sent and received over the window and per 10 s, the lowest interval rates, SID and sequence-loss counts or null where the stack does not fill them, duplicates, inactivity, `rx_silence` and `tx_silence` as `not_filled`, codec, ptime, RTCP round trip, hold, disconnect, class per direction, verdict and reasons); never a number, address or SDP. Records made before round 28 keep round 26's pass.
- **The passive call watch** (`OwnerCalls.kt`, `PhoneStateReceiver`, `CallWatchService`). Android's PHONE_STATE broadcast (protected, sent by the system) starts a watch of every real call. Once a second it reads the registry (DUMP) for each slot and records in the private ledger (`calls` in the state, at most 120): direction, whether it rang, was answered and went ACTIVE, the bearer readings at the start, at ACTIVE and at hang-up, RTP received and sent, inactivity, duration and the disconnect cause. Never the number: the mailbox comparison happens in the parser, and the broadcast's number extra is never read. An emergency call, or the app's own mailbox call, leaves nothing here.
- **The app's own "calls out" call** (`core/MailboxCall.kt`, `MailboxCaller`; `AndroidCallDevice` in `OwnerCalls.kt`), only the fallback:
  - when: after an apply (a provisional keep without calls out since it was applied), after others' reports point at a voice entry's on value of this SIM's cell and no real outgoing call on its bearer passed within 3 days, or weekly per kept voice entry when none passed that week (`CallsOutPlan`). At most one call per feature and bearer a night; only in the night window and the whole silent window;
  - the number: only the SIM's own entry of the bundled mailbox table (`CallTargets.mailboxFor`: the SPN rule, then the network code), a plain 3 to 6 digit code, not on the fixed emergency list, not a service prefix (0, 11x, 19x), not marked unverified, and Android says it is not an emergency number (`TelephonyManager.isEmergencyNumber` and the subscriptions' emergency lists; an exception refuses). Telecom's call placement on the SIM's own phone account is the only dial in the code and checks the number once more;
  - never in round 25's LB6 refusal states (a call up, emergency callback or SMS mode, an emergency call within 10 minutes, 10 minutes after a boot or a system restart when the call watch cannot rule out a call just before it, roaming, anything unreadable), with the stop flag set, or while Telecom says or cannot say whether an emergency call is up;
  - the voice-call stream to its lowest volume and muted (`MODIFY_PHONE_STATE`), the microphone muted, both again once the call is up, and given back afterwards; a stream that cannot be muted refuses the call;
  - while it runs: an emergency mark (the registry's emergency number changing, or Telecom's emergency call) aborts at once, gives the sound back and touches no call; another call ringing, or the charger pulled, ends the app's call and the result does not count. The app ends its call itself after ACTIVE, once round 28's window can be judged (at least 15 s and 3 CallQuality reports over 10 s, at most 25 s), through Telecom's end call (which never ends an emergency call);
  - for VoLTE while IMS runs over Wi-Fi, IMS first moves to LTE inside the non-persistent Wi-Fi calling off override (as VoLTE's measurement does), reverted with proof after the call;
  - afterwards exactly that call's call log entry is deleted: the one outgoing entry to the mailbox number created at the call's time, by its own ID; with any other count nothing is touched;
  - **dry run** (`CallsOutMode.DRY_RUN`, the default until the owner turns "Test calls out automatically" on): every guard runs, nothing changes, and the log says what would be dialled ("dry run: would dial the LIDL Connect (Vodafone network) mailbox 5500 on slot 1 for Wi-Fi calling over Wi-Fi …; nothing dialled (dry run)"). "Try the mailbox call without dialling" in Details, or `adb shell am start -n io.github.open_carrier_data.check.owner/io.github.open_carrier_data.check.owner.OwnerActivity --ez calls_out_dry_run true`, runs one.
- **Provisional keep for changed voice values** (`Provisional`; round 26 rule change 7). A VoLTE or Wi-Fi calling on that differs from the phone's own value is kept past its night only after calls out passed on its bearer; it then reads "incoming not yet seen". It reverts by itself (a drop step in any silent window, through the guards) on a measured incoming failure on its bearer (answered but never ACTIVE, ACTIVE on another bearer than IMS was on when it rang, a circuit-switched call included, dropped under 20 s with an abnormal cause, or no audio stream received on two answered calls on separate days), on a measured calls-out failure (for a real call's missing audio stream, again two calls on separate days), when its night ends without calls out, or 7 days after the apply without incoming evidence. A declined or missed call is not a failure. A changed VoNR value has no bearer proof and is not kept. Values equal to the phone's own need nothing new; data and APN keeps are unchanged.
- **"Re-tested by OCD"** (`Retested`; round 26 rule change 9): from this phone's L2 or L3 only, with the level, the method (mailbox call or real call, per leg), the build and the date, for 90 days: "re-tested by OCD: calls out over Wi-Fi, incoming not tested (build …, 2026-10-21) (audio from packet counts)". The pointer report's `works` for VoLTE and Wi-Fi calling now needs L3 (its call test `t2`).
- **MMS** (`core/MmsProbe.kt`, `OwnerMms`; round 26 rule change 6). Where a network ended MMS (since round 32 OCD's published list at the pinned commit, then the bundled `app/src/owner/assets/mms-ended.json` for the networks it does not cover yet, today 26201 and 22801; see **Round 32** below), Details says "MMS: not checked, the network no longer offers MMS (Vodafone Deutschland states MMS ended on 2023-01-16)". Elsewhere MMS stays a test target, checked every 14 days by a free, silent probe: Android's MMS network for the SIM (`NET_CAPABILITY_MMS`), one HTTP GET to the MMSC of the phone's MMS APN row through its MMS proxy, and the status line. Any HTTP answer is "MMS access point reachable", never "MMS works". It never sends an MMS (it costs money), never a POST, and not while roaming or with mobile data off.
- **Optional incoming SMS check** (`core/SelfSms.kt`, `OwnerSelfSms`, `SelfSmsReceiver`), off by default ("Check incoming SMS over IMS" in Details, with the note that it may cost an SMS): about once a week at night, one data SMS to the phone's own number on the app's port 16123 (always a port, never a port-less text, never a Type 0 SMS), only with SMS over IMS registered and not roaming. It coming back is a partial check that says nothing about calls; it is never "works". The own number is read for the send and never kept. "Send a test SMS now" in Details (or `--ez self_sms_now true` over adb, below) sends one such SMS at once, under the same refusals plus no call and no emergency state; the weekly switch stays as it is.
  - **SMS both ways over IMS** (round 29) rests on Telephony's own word for each leg, measured on the S20 on 2026-10-24 (LineageOS 24.0, AOSP ImsStack, o2 over Wi-Fi calling). Out: the SMS_SENT result's `ims` extra (`SMSDispatcher.SmsTracker.mUsesImsServiceForIms`, true when Telephony handed the SMS to the IMS service; the sent PendingIntent is mutable and names the receiver, so the extra arrives). Back: the inbound SMS handler's own record in `dumpsys isms` (DUMP, `core/SelfSms.kt` `InboundSms`), read at receipt in the SIM's own section: an SMS the IMS service received arrives as `EVENT_INJECT_SMS` (ImsSmsDispatcher injects it, `isOverIms` true; the only other source is `SmsManager.injectSmsPdu`, carrier-privileged apps only), an SMS over CS or SGs as `EVENT_NEW_SMS` from the radio. Only the record's kind and time are read; when another SMS arrived the other way between the send and the receipt, the way back is unknown. The receipt also records IMS registered with SMS at that moment (ImsMmTelManager), the indirect signal, which settles nothing on its own. The broadcast itself carries no transport (`pdus`, `format` 3gpp on both paths, `messageId`, the subscription and slot), and the ImsStack dump and Telephony's SMS analytics keep no per-SMS transport. SMS both ways is `received` with IMS registered for SMS at the send, out `ims` and back `ims`; the log says each leg, for example "the test SMS went out through the IMS service and came back through the IMS service (Telephony: injected by IMS); IMS registered with SMS at receipt; SMS both ways over IMS: settled". It is the `self_sms` settled result of the pointer report and, since round 30, of the `sms_both_ways` record (round 29's runtime layer used it as its durable class check).

**The safety floor**, the same for both routes and enforced in code with tests:
- the key guard: never a key matching `emergency|e911|ecbm|wps|tty|rtt|iwlan\.`, and only the five feature switches; never an emergency APN row. The Shizuku service checks the guard and every argument again;
- never an emergency call, and only one number ever dialled (round 26 rule change 4): the SIM's own allowlisted mailbox, under the emergency-number check, the service-prefix refusal and these refusals, muted, at night; an emergency mark during that call aborts it at once without touching any call. The app never answers a call, never sends a menu digit (DTMF) and never sends an SMS or MMS but the optional data SMS to its own number on its own port;
- refusals that fail closed: nothing changes in a call, in emergency callback mode (or emergency SMS mode), within 10 minutes of an emergency call (counted from the first sighting of the registry's emergency-call field, which still counts for its 10 minutes when a restart has cleared the field, or from the end of an emergency call the call watch saw), within 10 minutes after a boot or a restart of the system server alone **only when the call watch cannot rule out a call just before it** (below), while roaming (national roaming included), or when one of these cannot be read;
- **the restart check, an event since 2026-10-25** (`RestartWindow`, `CallSightings`). A reboot or a soft restart clears the registry's emergency-call field, so builds before refused every change for a fixed 10 minutes after each ("the phone started less than 10 minutes ago", 30 minutes of a first-use check on 2026-10-25 lost to it and to the idle wait). The reason stays: an emergency call just before the restart. It is now checked as an event. `PhoneStateReceiver` is direct-boot aware and notes when every call starts and ends (PHONE_STATE, which the system sends for every call, an emergency call included, also before the first unlock), in device-protected storage, times only, never a number; the call watch marks a call Telecom called an emergency call. After a restart, changes are refused only while a call that was not the app's own mailbox call ended less than 10 minutes ago and before the restart (a call still open at the restart counts as ending with it), or while the watch did not cover those 10 minutes: no record yet, or the app was force-stopped, stopped by the user or updated since (`ApplicationExitInfo`). Then the old 10 minutes apply. Calls since the restart are the registry's. The idle moment's and the emergency data test's hour after a restart follow the same check with 60 minutes. The start of a soft restart comes from `sys.system_server.start_elapsed`, or, where SELinux hides it, from the first sighting of that server by boot ID, zygote's PID and start count;
- never Wi-Fi, never the device log: VoLTE is measured inside a non-persistent override, and the IWLAN state comes from dumps, so Android never asks for "access to all device logs";
- a voice off is kept only with voice service measured (a call went active with it off); without a call it is always reverted, and a call that does not connect is a stop event (lost voice);
- overrides are never persistent: `cmd phone cc set-value` without `-p`, or `CarrierConfigManager.overrideConfig(subId, bundle)` with persistent false. Every change is recorded before it runs, every revert is proven against the dump taken before the first change, and a revert that cannot be proven sets a stop flag that turns the write path off until the owner clears it;
- the write gate: the S20 (`x1s`, `SM-G981B`) on its LineageOS build and a route; the A50 and every other phone stay read-only and the screen says why;
- round 25's first-use order: until one override has been left live through a reboot and was gone afterwards (the screen's "Start restart check" in Details, then a restart), nothing is kept, no off is tested and a background run changes nothing. The two lab steps before it are the owner's to keep and are not on the screen: 1. only after the S20 build's boot check, never together with another build change; 2. the first apply on the cable, with a lab `--read` before and after.

**Two routes behind one interface** (`OwnerPhone`), picked at run time; the log notes the route whenever it changes:
- **Privileged system app** (the target form, used automatically): when the APK sits in a `priv-app/` folder, `app/src/owner/priv-app/privapp-permissions-ocd-check-owner.xml` grants `MODIFY_PHONE_STATE`, `READ_PRIVILEGED_PHONE_STATE`, `READ_PRECISE_PHONE_STATE`, `WRITE_APN_SETTINGS`, `DUMP` and `PACKAGE_USAGE_STATS`, and `CarrierConfigManager.overrideConfig(int, PersistableBundle)` is reachable (the same file puts the app on the hidden-API allowlist; the gate looks the method up without calling it), the app uses `overrideConfig` (the system API that is never persistent) and the telephony provider directly. The carrier config, the registry (call state, roaming, the emergency number since boot, the callback-mode timers, the IMS data connection on each transport with its fail cause) and the power state are read with `dumpsys` as the app; the IWLAN data service and QNS (the tunnel, its errors, and QNS's Wi-Fi restriction for IMS, which the log used to show as a back-off) with `dumpsys activity service`, which needs `PACKAGE_USAGE_STATS` besides `DUMP`. `READ_LOGS` is gone: Android asks the owner before an app reads the log, and a privileged app cannot skip that prompt. The phone service's dump is closed to an app (`dumpsys activity service com.android.phone` goes through ActivityManager, which also wants `PACKAGE_USAGE_STATS`), and SELinux keeps `priv_app` from `ril.cdma.inecmmode`; on the first system-app run (2026-10-19) every step was refused with `emergency_state_unreadable` for that reason. Shizuku must grant the app once in its own dialog. **Round 30: the whole dataset, tests decide** (OCD's rule round 30, decided 2026-10-25; the S20 workspace's `reports/OCD round 30 dataset spec.md`, section 12.3 for this app; the owner's decisions of the same day on its section 11). On the owner's ROM built with `OCD_CARRIER_DATASET` (vendor/extra `carriersettings/`), CarrierSettings replaces Google's carrier data with OCD's dataset and is its only installer. - **The pull** (`core/Dataset.kt`). The whole dataset of the commit the main pin took (above), so F1 holds by construction: `generated/ocd-dataset/manifest.json`, `profiles.json`, `google-lane.json` (only while the manifest says `"google_lane": "included"`), `apn-index.json`, `generated/android/apns-conf.xml` and `generated/devices/device-records.json`.

- **The idle moment** (`IdleMoment`), for background runs only, as they must not disturb the person using the phone: no call ringing, up or held and no real call in the last 10 minutes (the app's own mailbox calls do not count); the screen off for 2 minutes; no media playing or recording; not in emergency callback or emergency SMS mode; no emergency call in the last 60 minutes (the hour after a restart waits only when the call watch cannot rule one out); the battery at 20 % or charging; not roaming. No night and no Wi-Fi requirement; Wi-Fi calling tests need Wi-Fi.
- **"Test now" means now** (the owner's rule of 2026-10-25, "what can be done now should be done now"). Only the guards that name a harm stop it: a call (ringing, up or held), emergency callback or SMS mode, the 10 minutes after an emergency call, roaming and "changes halted". Its pull has no network constraint (a pull that fails offline never holds the test up), and a second "Test now" while one runs is not queued again and never cancels it; "Stop test" cancels it.

Before it installs or tests, a run (background runs too, and the cleanup when something is recorded as live) waits for what a test needs after a boot, a SIM change or a restart: the SIM loaded (TelephonyManager's SIM state; a slot still loading holds the run only while no SIM is loaded at all, since an empty second slot can stay `NOT_READY` for good, as the S20's does), CarrierSettings's config served for the slot (its `mConfigFromDefaultApp` layer in `dumpsys carrier_config` and `mHasSentConfigChange` true), and IMS in a stable state: registered, or not registered with no attempt for a minute (or on two looks that name why its last attempt ended). It looks every 5 s for at most 2.5 minutes; a phone that has run for a while is ready at the first look. When the bound passes, the run installs and tests nothing and says what was missing.

It works with the screen off and when the page is already open (the page is `singleTop`, so `am start` on its open task delivers the extra to `onNewIntent`; before, Android only brought the task to the front and dropped the extra, which hit the other extras too); the device log tag `OcdCheckTestNow` says when the request came and when the dataset step started and ended, and the app's log (Details) has the run's lines.

Before, the open page re-read and re-parsed that file twice every 3 s with the screen off and rewrote it every 15 s, which freed about 10 MB every 30 s.

It goes only into the `Authorization` header to `api.github.com` over HTTPS. It is never logged, never in the state, a report or the screen, and the field clears once it is stored. A classic token (`ghp_…`) is refused, because it cannot be limited to one repository's issues.
- **When GitHub refuses it** (expired, revoked, missing permission: HTTP 401, 403, 404, 410 or 422), nothing more is sent until a token is entered again, and the screen says so. Offline or a 5xx is tried again later.
- **Without a token** nothing is sent. "Open report on GitHub" opens the prefilled form as before, and it stays available with a token too.
- **Tests.** `MessagesTest` covers Telephony's inbound record (the S20's own `dumpsys isms` lines), the way out from the send's answer, and when SMS both ways holds. `AutoReportTest` covers L2 and L3 from the call ledger, the measured failures, the build and the time a level holds, SMS both ways, where a level attaches, the report and the automatic issue against the public schema and form, what is sent when and again, a refused token, the token's form, and that nothing written holds the token. `GuardTest` allows one HTTP POST in the owner build, in `OwnerReports.kt` to the issues API, with no log in that file. The automatic issue was also checked with the public bot's `check_issue`.

**How to create the token (the owner, on GitHub).** The app never creates one; you create it and enter it on the phone yourself.
1. On GitHub: **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token** (<https://github.com/settings/personal-access-tokens/new>).
2. **Token name:** for example `OCD Check S20 reports`. **Expiration:** 90 days is a good choice (GitHub offers up to a year, or a custom date); set a reminder to make a new one before it runs out.
3. **Resource owner:** `open-carrier-data`. If the organisation requires approval for fine-grained tokens, approve the request as its owner, or allow fine-grained tokens under the organisation's **Settings → Third-party Access → Personal access tokens** first.
4. **Repository access:** **Only select repositories** → `open-carrier-data/open-carrier-data`. No other repository.
5. **Permissions → Repository permissions → Issues: Read and write.** Leave every other permission at **No access**; GitHub adds **Metadata: Read-only** by itself, which every token has. No account permission.
6. **Generate token** and copy it (it starts with `github_pat_`).
7. On the phone: **Settings → Network & internet → Open Carrier Data → Details → Reports**, paste it into **GitHub token** and tap **Save token**. The row then reads "On: settled results go to Open Carrier Data as issues under your GitHub account", with the last report sent.

To stop: **Remove token** on the same row deletes it and its key from the phone. To end it everywhere, revoke it on GitHub under **Fine-grained tokens** (a lost phone included); the app then gets 401 and stops. The issues it sent are public under your account, like the ones you submit by hand.
